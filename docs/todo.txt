SECTION 2 — HARDWARE VERIFICATION (required before deploy)
================================================================================

T2 — Verify nitro WAN MAC address                              [🔴 CRITICAL]
----------------------------------------------------------------------
The wan_mac for nitro (TP-Link Archer AXE75) in network_devices.yaml was
identical to ultra64's WAN NIC MAC (24:2F:D0:D1:2E:31). Two different
physical devices cannot share a MAC address. One of these is wrong.

The wan_mac in network_devices.yaml has been set to "VERIFY_HARDWARE".

Steps:
  1. Physically check the MAC address printed on the WAN port of the
     TP-Link Archer AXE75 (nitro).

  2. Update data/inventory/network_devices.yaml:
       wan_mac: "<actual nitro WAN MAC>"

  3. Also verify ultra64's WAN NIC MAC is correct:
       # On the router:
       ip link show enp1s0f0
     Confirm it matches interfaces.wan.mac in data/nodes/ultra64.yaml
     (currently: 24:2F:D0:D1:2E:31)

  4. Run: make compile

  NOTE: The 10-wan.link.j2 template uses interfaces.wan.mac to pin the
  WAN interface via MACAddress=. If this is wrong the WAN interface will
  not come up and you will lose internet connectivity.

T3 — Capture real SSH host keys                                [🔴 CRITICAL]
----------------------------------------------------------------------
data/nodes/ultra64.yaml host_keys is intentionally empty (placeholder
removed in ef1c458). Ansible will connect with StrictHostKeyChecking no
but known_hosts will not be populated for manual SSH hardening.

Steps:
  1. Ensure ultra64 is reachable on 10.64.0.1

  2. Run:
       make known-hosts

  3. Paste the output into data/nodes/ultra64.yaml under host_keys:
       host_keys:
         ssh-ed25519: "AAAA..."
         ssh-rsa: "AAAA..."

  4. Run: make compile
     This regenerates ansible/generated/known_hosts with real keys.

T4 — Add vault_crowdsec_bouncer_api_key to vault               [🟠 HIGH]
----------------------------------------------------------------------
The CrowdSec bouncer config template references vault_crowdsec_bouncer_api_key.
Without this the bouncer will fail to start after deploy.

Bootstrap sequence:
  Step 1 — Add placeholder to vault now:
    make vault-edit
    # Add this line:
    vault_crowdsec_bouncer_api_key: "PLACEHOLDER_run_cscli_after_install"

  Step 2 — Run full deploy (installs CrowdSec):
    make deploy

  Step 3 — On the router, generate the real key:
    ssh root@10.64.0.1
    cscli bouncers add firewall-bouncer
    # Copy the printed key

  Step 4 — Update vault with real key:
    make vault-edit
    # Replace PLACEHOLDER with the real key

  Step 5 — Re-deploy just crowdsec role:
    make deploy-role ROLE=crowdsec

T5 — Verify Headscale DERP port                                [🟠 HIGH]
----------------------------------------------------------------------
data/services/headscale.yaml has derp.port: 3478 (standard STUN port).
This value is used in the nftables firewall rules. If wrong, DERP traffic
will be blocked or the wrong port will be opened.

Steps:
  1. After Headscale is installed, check its config:
       ssh root@10.64.0.1
       cat /etc/headscale/config.yaml | grep -A5 derp

  2. If the port differs from 3478, update:
       data/services/headscale.yaml → derp.port: <actual port>

  3. Run: make compile && make deploy-role ROLE=firewall

T6 — Verify *.rsk.al wildcard DNS target                       [🟠 HIGH]
----------------------------------------------------------------------
data/services/dns.yaml has *.rsk.al → network: 64, host: 202.
This means all *.rsk.al domains resolve to 10.64.0.202 (Caddy proxy LXC).

Confirm this is correct:
  - host: 202 → wildcard resolves to Caddy proxy LXC (10.64.0.202) ✓ likely correct
  - host: 1   → wildcard resolves to the router itself (10.64.0.1)

If your Caddy reverse proxy LXC is NOT at 10.64.0.202, update:
  data/services/dns.yaml → custom_dns *.rsk.al entry → host: <correct host>
  Then run: make compile

SECTION 4 — POST-DEPLOY SETUP
================================================================================

T7 — Bootstrap step-ca (internal CA)                           [🟠 HIGH]
----------------------------------------------------------------------
Caddy sovereign TLS for *.rsk.al domains requires step-ca to be
initialised and running before Caddy can obtain certificates.

Steps:
  1. After deploy, SSH to router:
       ssh root@10.64.0.1

  2. Initialise step-ca if not already done:
       step ca init

  3. Verify step-ca is running:
       systemctl status step-ca

  4. Re-run Caddy role to trigger cert acquisition:
       make deploy-role ROLE=caddy

T8 — Enroll Headscale users and devices                        [🟠 HIGH]
----------------------------------------------------------------------
After Headscale is deployed, no users or devices are enrolled.

Steps:
  1. Create a user:
       make headscale-nodes   # verify headscale is running first
       ssh root@10.64.0.1
       headscale users create raskal

  2. Generate a pre-auth key:
       make headscale-key
       # or manually:
       headscale preauthkeys create --user raskal --reusable --expiration 720h

  3. Enroll each device:
       tailscale up --login-server https://wfc.raskal.io --authkey <key>

  4. Verify enrollment:
       make headscale-nodes

T9 — Set up Headscale DB backup schedule                       [🟡 MEDIUM]
----------------------------------------------------------------------
The Headscale DB at /var/lib/headscale/db.sqlite contains all enrolled
nodes, users, and pre-auth keys. Losing it requires re-enrolling all devices.

Steps:
  1. Add a systemd timer or cron job on ultra64:
       # Example cron (daily at 2am):
       0 2 * * * /bin/bash -c 'mkdir -p /root/headscale-db-backups && \
         cp /var/lib/headscale/db.sqlite \
            /root/headscale-db-backups/db-$(date +\%Y\%m\%d-\%H\%M\%S).sqlite && \
         ls -t /root/headscale-db-backups/db-*.sqlite | \
            tail -n +31 | xargs rm -f 2>/dev/null'

  2. Or use: make headscale-backup before any maintenance.
